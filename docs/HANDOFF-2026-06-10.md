## Toolchain — READ THIS before running web tests

**The "local vitest hangs / times out" problem is SOLVED. It was never memory.**

- Root cause: `apps/web/vitest.config.ts` used `pool: 'vmForks'`. On **node 24**, vmForks creates a `vm`-isolated context per fork and compiles modules inside it — pathologically slow: a single file showed `setup 555s / environment 355s / ~929s total` (or a 60s worker-handshake timeout). Isolation check: `new (require('happy-dom').Window)()` instantiates in **137ms**, so the cost was entirely the vmForks/vm layer.
- Fix (`78ed3ff`): `pool: 'threads'` (removed `maxWorkers: 1`). Same file runs in **6.4s (~146×)**.
- **DO**: `pnpm -F web test` or `node_modules/.bin/vitest run <file>` (uses the config's `threads`).
- **DON'T**: pass `--pool=forks` / `--pool=vmForks` — that re-introduces the hang. (Earlier in the history I repeatedly did this and misattributed it to memory; ignore any older note that says "local vitest must be run single-file due to memory".)
- Residual: first cold transform/import is slow (3 files ≈176s) — Vite dep cache warms it up; not blocking.
- Local `tsc -b` is also unreliable on this machine (I/O-bound, can hang) — trust the **server docker build** for the real type check.
