## 三、reopen 功能:评估后【暂不做】;改为给「结束」加二次确认 ✅ 已完成(本地,待部署)

> **2026-06-04 已实现**:`TaskManagePanel.tsx` 新增 `requestTransition(action)`,仅 `action==='end'` 走 `Modal.confirm`(标题/正文如下),onOk 才 `transitionTask(id,'end')`;其它转移直接执行。`TaskManagePanel.test` 9/9(+3 TDD 用例)、`Dashboard.test` 37/37、`tsc`/`eslint` 干净。**纯前端,待 `rsync apps/web/src/ + up -d --build web` + chrome 实测**。下文为原方案记录。

**背景**:用户测试时误把 demo 任务点成「已结束」,发现没有「重新发布」按钮 → 任务状态机 `ended` 是终态、无任何转出动作(确认无误,见下)。

**决定(2026-06-04,与用户确认):不做 reopen。** 理由:① `ended` 终态是真实标注平台的标准设计(要再收数据应新建任务 / 批次,而非复活已结束任务);② 这个"需求"源于测试误操作,非真实产品需求,违反 YAGNI;③ 非赛题考察点,评委不会期待"复活已结束任务",加了大概率是负分项。

**改为做(对症、更小、更有产品味)——给「下线 / 结束」加二次确认弹窗:**
- 落点:`apps/web/src/modules/owner/TaskManagePanel.tsx` 的 `runTransition(action)` / 底部动作按钮处。仅对 `action==='end'`(标签「下线」)先弹 `Modal.confirm`(本仓已用 Semi `Modal.confirm`,测试里有 `mockModalConfirm` 可参考),确认后才调 `transitionTask(id,'end')`。其它转移(publish/pause/resume)不弹。
- 文案:标题「确定结束该任务?」+ 正文「结束后任务变为『已结束』,**不可恢复**,标注员将无法再领取该任务的题目。」
- 测试:`TaskManagePanel.test` 加「点『下线』先弹确认、取消则不调用、确认后才 `transitionTask(id,'end')`」。
- 验证 + 部署:纯前端,`tsc`/`eslint`/`vitest TaskManagePanel.test` + `rsync apps/web/src/ + up -d --build web`。

### 附:reopen 实现方案(已评估【暂不做】,以后若真有需求——如老板要求误操作可回滚——再照此做)

**现状(只读核实)**:
- 后端 `apps/api/internal/statemachine/task.go:23-28` `taskTransitions`:仅 `draft→publish→published`、`published⇄paused`(pause/resume)、`published|paused→end→ended`。**无 `ended→*`**。
- 前端 `apps/web/src/modules/owner/taskManageHelpers.ts:151-163` `availableTransitions('ended')` 落到 `default: return []`。
- 转移统一走 `apps/api/internal/handler/task.go:407 transitionTask(...)`(`PublishTask`/`PauseTask`/`ResumeTask`/`EndTask` 各调它,带 `requireTemplate`);前端 `client.ts transitionTask(taskId, action)` 的 action 类型是 `'publish'|'pause'|'resume'|'end'`。

**实现方案(后端 + 前端,无 schema 迁移)**:

### 后端
1. `statemachine/task.go`:加事件常量 `TaskEventReopen = "reopen"`;在 `taskTransitions` 加
   `{TaskEnded, TaskEventReopen}: {From: TaskEnded, Event: TaskEventReopen, To: []string{TaskPublished}}`。
   - 补该转移的单测(`task_test.go` 现有转移表测试同款)。
2. `handler/task.go`:加 `func (h TaskHandler) ReopenTask(c *gin.Context) { h.transitionTask(c, statemachine.TaskEventReopen, true) }`
   (`requireTemplate=true`:已结束任务本就有过模板,守一道防止 template_id 被清空的边界)。
   - `transitionTask` 的乐观更新 `WHERE id=? AND status=?` 天然适配,无需改。
3. 注册路由(`task.go` 路由处,与 publish/pause/resume/end 并列):`POST /tasks/:taskId/reopen`,owner/admin 鉴权。
4. **重要业务确认**:reopen → `published` 后,该任务未完成的 item(qa_quality 23 道未完成)应重新可被领取。核对 `claim`/领题逻辑只认 `task.status=published`(应该是),则无需额外改;若 end 时把 task_items 也置了终态,reopen 要一并恢复——**动手前查 `EndTask`/end 时对 task_items 做了什么**。

### 前端
1. `taskManageHelpers.ts`:`TaskTransition` 加 `'reopen'`;`availableTransitions('ended')` → `return ['reopen']`;`TRANSITION_LABELS.reopen = '重新发布'`。
2. `client.ts`:`transitionTask` 的 action 联合类型加 `'reopen'`,内部 `POST /tasks/${id}/reopen`(或复用现有 transition 端点映射)。
3. `TaskManagePanel.tsx`:底部动作条已按 `availableTransitions(selected.status).map(...)` 渲染按钮,加了 reopen 自动出现「重新发布」按钮,**无需改组件**。
4. 测试:`TaskManagePanel.test` 加「ended 任务显示重新发布、点击调 transitionTask(id,'reopen')」;`client.test` 加 reopen 调用断言。
